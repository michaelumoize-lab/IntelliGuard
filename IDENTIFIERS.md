# IntelliGuard — Entity Identifier Strategy & Reference Architecture

## 1. Overview & Dual-Identifier Strategy

IntelliGuard enforces a **dual-identifier architecture** across all primary application entities. This architecture cleanly separates:
1. **Internal Identity (System & Database Tier)**: Machine-optimized, globally unique, time-ordered primary keys (`UUIDv7`) generated directly by PostgreSQL.
2. **Business Identity (Operational & Public Tier)**: Human-readable, prefixed codes (e.g., `PER-17BF059C1234`) generated by the application layer for UI display, operational logging, audits, and external API communication.

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        DUAL-IDENTIFIER CONTRACT                        │
├──────────────────────────────────┬─────────────────────────────────────┤
│      INTERNAL DATABASE IDENTITY  │      PUBLIC BUSINESS IDENTIFIER     │
├──────────────────────────────────┼─────────────────────────────────────┤
│ • PostgreSQL native uuidv7()     │ • Node.js crypto randomBytes(6)     │
│ • Canonical UUID format          │ • Entity prefix + 12-char uppercase │
│ • Primary keys & Foreign keys    │ • Unique constraint in database     │
│ • High-performance B-tree index │ • Human-readable operational code   │
│ • Never exposed unnecessarily    │ • Surfaced in UI, badges, logs, API │
└──────────────────────────────────┴─────────────────────────────────────┘
```

## 3. Architectural Rationale

### 3.1 Why UUIDv7 for Internal Primary Keys?
1. **Time-Ordered Locality**: Unlike UUIDv4 (which distributes uniformly across the B-tree index causing severe cache misses and page fragmentation at scale), UUIDv7 embeds a high-resolution millisecond Unix timestamp in its first 48 bits. This ensures sequential append patterns, optimal B-tree page caching, and low insert latency.
2. **Global Uniqueness**: Generates non-colliding IDs across distributed edge nodes, background workers, and microservices without coordination.
3. **Security Against Enumeration**: Unlike sequential integers (`SERIAL` / `BIGSERIAL`), UUIDv7 cannot be guessed or crawled sequentially by attackers.

### 3.2 Why PostgreSQL Generates UUIDv7 Values?
- Neon PostgreSQL 18+ provides native C-level `uuidv7()` execution (`SELECT uuidv7()`).
- Generating IDs inside PostgreSQL ensures zero clock drift between application instances, eliminates external npm dependencies (e.g., `uuid` or `uuidv7` packages), and standardizes default generation for raw SQL inserts, migrations, and ORM operations alike.
- Prisma 6/7 represents this natively as:
  ```prisma
  id String @id @default(dbgenerated("uuidv7()")) @db.Uuid
  ```

### 3.3 Why Business Identifiers are Separate?
- **Cognitive Load & Usability**: Full UUID strings (`0192e4f0-466d-784e-b5c6-993d0f7724ac`) are difficult to read, speak over communication channels, or transcribe during security incidents.
- **Operational Clarity**: A prefix (`PER-`, `DEV-`, `ALT-`) immediately indicates the entity type to administrators, security staff, and auditors.
- **Decoupling**: System internals (such as database migrations, primary key restructuring, or partitioning) never alter external business codes referenced in printed badges, physical cards, or external tickets.

### 3.4 Why Business Identifiers are NEVER Used as Foreign Keys?
- Relational integrity requires immutable, compact, fixed-size primary and foreign keys (`uuid` 16 bytes binary).
- Using business codes as foreign keys degrades join performance, bloats index sizes, and creates cascading update overhead if business identifiers are modified or reformatted.

## 4. Business Identifier Generation & Collision Avoidance

Business identifiers are generated on the server using Node.js cryptographic randomness (`frontend/lib/identifiers.ts`):

```ts
import { 
  generatePersonCode, 
  generateDeviceCode, 
  generateFaceEmbeddingCode, 
  generateRecognitionEventCode, 
  generateAlertCode, 
  generateAccessLogCode 
} from "@/lib/identifiers";
```

### 4.1 Suffix Specifications
- **Entropy**: 6 bytes of cryptographically secure random bytes (`crypto.randomBytes(6)`), converted to 12 uppercase hexadecimal characters.
- **Search Space**: \(16^{12} \approx 281.47 \times 10^{12}\) (over 281 trillion distinct combinations per entity).
- **Backward Compatibility**: Validated by `isValidBusinessIdentifier()`, which permits both modern 12-hex suffixes and legacy 8-hex suffixes (such as existing `PER-17BF059C` records).

### 4.2 Collision Handling Protocol
1. **Primary Defense**: Every business identifier column has a PostgreSQL `UNIQUE` constraint and index (e.g., `idx_person_code`).
2. **Application-Layer Resilience**: The `generateUniqueBusinessIdentifier` utility wraps generation in an automated retry loop (up to 5 attempts) before persisting:
   ```ts
   const code = await generateUniqueBusinessIdentifier(
     generateDeviceCode,
     async (candidate) => Boolean(await prisma.device.findUnique({ where: { deviceCode: candidate } })),
     { maxRetries: 5, entityName: "Device" }
   );
   ```
3. **Database-Level Safety**: If a race condition occurs, Prisma catches the `P2002` unique constraint violation and handles the retry or returns an actionable conflict response.

## 5. Protected Better Auth Authentication Schema

The following authentication models and database tables are **strictly protected** and excluded from this identifier strategy:

- `User` (`user`)
- `Session` (`session`)
- `Account` (`account`)
- `Verification` (`verification`)

### Invariants:
- Better Auth manages its own internal IDs (CUID / string tokens) and relationships.
- No UUIDv7 database defaults or business identifier columns are introduced to Better Auth tables.
- Foreign keys from application entities to users (such as `Alert.resolvedBy -> User.id`) continue to reference `User.id` as `TEXT` / `String`.

## 6. Current Database State & Zero-Downtime Migration Plan

### 6.1 Database Discovery & Baseline Inspection
Inspection of the production Neon PostgreSQL database (`bitter-silence-77159111`, pg_version 18) revealed:
- **Existing Records**:
  - `persons`: 3 rows (currently has `person_code` with 8-hex format)
  - `devices`: 3 rows (has `serial_number`, no `device_code`)
  - `face_embeddings`: 3 rows (has pgvector `vector(512)`, no `embedding_code`)
  - `access_logs`: 240 rows (no `log_code`)
  - `alerts`: 115 rows (no `alert_code`)
- **Current Primary Keys**: All five tables currently use auto-incrementing integers (`id SERIAL NOT NULL PRIMARY KEY`).
- **Current Foreign Keys**: `person_id` (INT), `device_id` (INT), and `embedding_id` (INT) across `access_logs`, `alerts`, and `face_embeddings`.
- **Existing Application Contracts**: API routes (`/api/persons/[id]`, `/api/devices/[id]`, `/api/alerts/[id]`) parse `id` via `parseInt(params.id, 10)` and expect numeric parameters.

### 6.2 Safe, Multi-Phase Zero-Downtime Migration Strategy

Because in-place conversion of `integer` primary keys to `uuid` fails when referenced by foreign keys and breaks active integer queries, the transition to UUIDv7 follows a safe three-phase rollout:

```mermaid
flowchart TD
    subgraph Phase 1: Additive Business Identifiers
        A1[Add device_code, embedding_code, log_code, alert_code nullable columns]
        A2[Backfill existing records with generated business codes]
        A3[Add NOT NULL and UNIQUE constraints]
        A4[Ship lib/identifiers.ts and update record creation routes]
    end

    subgraph Phase 2: Additive UUIDv7 Columns
        B1[Add uuid_id UUID DEFAULT uuidv7 to all 5 tables]
        B2[Backfill uuid_id for existing historical rows]
        B3[Add uuid_person_id, uuid_device_id, uuid_embedding_id to dependent tables]
        B4[Backfill foreign keys via SQL JOIN on integer ids]
    end

    subgraph Phase 3: Primary Key Cutover
        C1[Drop old integer foreign key constraints]
        C2[Promote uuid_id to primary key]
        C3[Promote uuid foreign key columns]
        C4[Switch Prisma schema to String @id @default dbgenerated uuidv7 db.Uuid]
        C5[Update API route parameter validation from parseInt to UUID regex]
    end

    Phase 1 --> Phase 2 --> Phase 3
```

#### SQL Implementation Plan for Phase 1 (Business Identifiers):
```sql
-- Step 1: Add nullable columns
ALTER TABLE devices ADD COLUMN device_code TEXT;
ALTER TABLE face_embeddings ADD COLUMN embedding_code TEXT;
ALTER TABLE access_logs ADD COLUMN log_code TEXT;
ALTER TABLE alerts ADD COLUMN alert_code TEXT;

-- Step 2: Backfill existing records safely
UPDATE devices SET device_code = 'DEV-' || UPPER(SUBSTRING(MD5(RANDOM()::TEXT || id::TEXT) FROM 1 FOR 12)) WHERE device_code IS NULL;
UPDATE face_embeddings SET embedding_code = 'EMB-' || UPPER(SUBSTRING(MD5(RANDOM()::TEXT || id::TEXT) FROM 1 FOR 12)) WHERE embedding_code IS NULL;
UPDATE access_logs SET log_code = 'ACL-' || UPPER(SUBSTRING(MD5(RANDOM()::TEXT || id::TEXT) FROM 1 FOR 12)) WHERE log_code IS NULL;
UPDATE alerts SET alert_code = 'ALT-' || UPPER(SUBSTRING(MD5(RANDOM()::TEXT || id::TEXT) FROM 1 FOR 12)) WHERE alert_code IS NULL;

-- Step 3: Enforce NOT NULL and UNIQUE constraints
ALTER TABLE devices ALTER COLUMN device_code SET NOT NULL;
CREATE UNIQUE INDEX idx_device_code ON devices(device_code);

ALTER TABLE face_embeddings ALTER COLUMN embedding_code SET NOT NULL;
CREATE UNIQUE INDEX idx_embedding_code ON face_embeddings(embedding_code);

ALTER TABLE access_logs ALTER COLUMN log_code SET NOT NULL;
CREATE UNIQUE INDEX idx_access_log_code ON access_logs(log_code);

ALTER TABLE alerts ALTER COLUMN alert_code SET NOT NULL;
CREATE UNIQUE INDEX idx_alert_code ON alerts(alert_code);
```

## 7. Operational Guidelines for Engineers

1. **Creating Records**: Always use `lib/identifiers.ts` to populate business codes during record creation.
2. **Database Queries**: Query relations using internal IDs; query search bars and public lookups using business codes.
3. **API Contracts**: Return both identifiers in JSON payloads where appropriate (`id` for client state reconciliation, `personCode` / `deviceCode` for display).
4. **Data Migrations**: Never use `prisma migrate reset` or drop tables. All migrations must be additive and verifiable.
